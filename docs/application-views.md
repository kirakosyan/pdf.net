# Application integrations and viewer controls

FP-082 has an original source implementation in the optional `Fluent.Pdf.Applications` assembly. Core has no UI dependency. The standalone Reader remains independent and excluded from the SDK release. The requirement remains planned until its full qualification gates pass.

`PdfApplicationViewer` owns a private bounded `PdfViewSession`, cache and request lifetime. The caller supplies the immutable document snapshot and renderer registry and retains ownership of providers. Commands select physical pages and zoom from 0.25 to 4 at a 96 DPI base. Every render gets a generation; superseded requests cannot publish a frame. Hosts must compare generation again after dispatching queued work. State events run outside locks on the invoking/completion thread; hosts own dispatch and subscriber exceptions. Rendering and captured-text extraction each use the supplied finite operation policy. PNG encoding is a separate explicit operation with its own policy/report and borrowed output stream. Retained detached frames and host-decoded images belong to the host's memory budget.

Captured text is bounded raw mapped source text, excluding nonpainting text and hidden layers under the shared text profile. It is separate from raster display and does not establish author-confirmed logical reading order, visible ink or PDF/UA compliance. No OCR, renderer, network, document action or print destination is selected implicitly. `Print` requires explicit printer options and providers; opening or displaying a document never prints.

| Component | Declared applicability | Boundary |
| --- | --- | --- |
| Applications controller | net472, netstandard2.0, net8.0, net10.0; Windows/Linux/macOS subject to selected renderer | Core-only managed dependency, no toolkit types |
| WinForms sample control | Windows; net472, net8.0-windows, net10.0-windows | Real WinForms handles, MSAA document name/role, owned image lifetime |
| WPF sample control | Windows; same three targets | WPF dispatcher and UIA document peer, named text/status/buttons |
| ASP.NET browser sample | Windows/Linux/macOS; net8.0/net10.0 server, modern browser | Explicit loopback host and per-launch capability; private controller per request |

These are source applicability declarations, not qualified host or final-package claims. Native rendering requires independently provisioned assets supported by that host/runtime. Minimum Framework 4.7.2, other desktop architectures, complete native fidelity and manual screen-reader testing remain mandatory.

The Framework sample executables explicitly target `win-x64` with x64 platform selection. This keeps locked restore identical on Windows and Linux cross-build hosts instead of accepting the SDK's host-dependent default RID. Modern desktop examples use the installed Windows desktop runtime's process architecture; actual source observations record it separately.

The [WinForms](../examples/Fluent.Pdf.WinFormsSample/Fluent.Pdf.WinFormsSample.csproj), [WPF](../examples/Fluent.Pdf.WpfSample/Fluent.Pdf.WpfSample.csproj) and [browser](../examples/Fluent.Pdf.BrowserViewSample/Fluent.Pdf.BrowserViewSample.csproj) samples accept two explicit arguments: a local PDF path and an offline rendering XML configuration. The closed configuration root is `rendering` with `root`, `rid`, `worker`, `bridge` and `jobs` attributes. Each `asset` has a relative `file`, exact `bytes`, `sha256` and optional `native="false"` for managed assets. The existing isolated renderer checks all declared identities and its mandatory native sandbox. No assets are discovered or downloaded. Unsupported provider/content behavior rejects with stable diagnostics; there is no fixture fallback on this normal path. `--self-test` alone enables the explicitly labeled original constant-color renderer for application boundary checks. It does not render PDF content faithfully.

Buttons and local Page Up/Down, Home/End, Control plus/minus, Control zero and Escape gestures navigate, zoom and cancel. Tab uses each toolkit's normal focus order. Desktop captured-text controls preserve their own text navigation. Controls expose named rendered-image, captured-text, status and command elements. WPF and browser status use polite live announcements; full assistive-technology behavior requires manual qualification. Disposal cancels only the control's requests and releases its image/subscription lifetime; it does not dispose caller providers or the borrowed viewer.

The browser host serves bundled static assets and a read-only page API on loopback only. It prints an authorized local address whose random capability is in the fragment; JavaScript sends it in a header, never in a request URL. API requests reject missing/wrong tokens, non-loopback hosts and cross-site fetch metadata. There is no CORS or cookie authentication. Responses prohibit caching and framing, use a restrictive CSP and expose captured text through text properties. Four simultaneous page requests, finite surfaces and explicit rendering/encoding budgets bound this sample. It is a local developer integration, not a deployed multi-tenant web service. Public hosting requires a separate authenticated application with principal/document authorization, TLS and host isolation.

The C# and VB contract examples compile against the public controller with the same target mappings as other SDK examples. Future package-only consumers must replace project references with exact qualified package identities; packages remain blocked until every mandatory SDK gate passes.

`eng/test-application-views.ps1` runs six real Windows applications across the two toolkits and three runtime targets. `eng/test-browser-view.py` uses caller-provisioned Playwright/Chromium with its browser sandbox enabled to exercise actual DOM keyboard routes, focus, cancellation and the accessibility tree. Neither tool downloads a native PDF renderer. Independent PNG decoding checks emitted dimensions/pixels, not PDF rendering fidelity. [Exact clean-source observations](evidence/FP-082-source.json) record the SDK/browser checkpoint separately from the desktop runtime correction and actual host runs.

Full renderer/print integration, malformed-content/concurrency/endurance, actual minimum runtimes, Windows/Linux/macOS browser matrices, high-contrast/DPI/localization, manual screen-reader behavior and exact final package consumers remain mandatory. No stable production gate is waived.

Actual Windows source run [39990658862](https://github.com/kirakosyan/pdf.net/actions/runs/39990658862), head `3d43215`, passed all six WinForms/WPF applications on current Framework 4.8.9363.0, .NET 8.0.32 and .NET 10.0.13, each in an x64 process. WinForms checks that Home keeps PDF selection unchanged while captured text has focus, then exercises page navigation from a focused command control through actual key preprocessing. WPF checks its real Document peer and routed key handling. The same run passed both real-browser host profiles. Prior restore and focus-test failures remain in the evidence lineage; minimum Framework and manual assistive-technology/fidelity qualification remain open.
