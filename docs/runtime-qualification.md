# Runtime and architecture evidence

FP-086 requires exact packages on 22 mandatory lanes. The [lane inventory](../specs/runtime-lanes.json) matches the unchanged [release manifest](../specs/release-readiness.json): Windows/Linux/macOS x64/ARM64 on .NET 8 and .NET 10, explicit netstandard2.0 consumers on modern .NET, and Windows x86/x64 on both actual minimum Framework 4.7.2 and current Framework. Source declarations and consistency checks do not qualify a runtime, feature or package. The requirement remains planned.

The runtime identity test records observations from the same process that executes the SDK suite: OS family/description and architecture, process architecture, RID, actual CLR/version, core-library name/file version/SHA-256, live Windows Framework release key, culture, and all 15 loaded SDK assembly targets/SHA-256/module IDs. Existing readable runtime/asset output remains available. It does not construct a runtime version from a target-framework attribute.

`eng/check-runtime-evidence.py` binds that observation to the TRX. Every required result must pass: positive complete counts, zero failure/skip/abort/error/timeout and no duplicated/missing test or execution ID or identity observation. Native modern lanes require the expected OS architecture and process architecture, so emulation cannot silently replace a native host. Windows x86 Framework consumers explicitly run on the declared x64 host. Loaded SDK targets must match the requested normal or fallback asset on every assembly.

Minimum Framework 4.7.2 requires the live installed release value 461808 or 461814, an actual Framework process using `mscorlib`, and 4.7-series core-library/runtime observations. A net472 assembly under Framework 4.8/4.8.1 rejects for that lane. Current Framework requires its actual serviced installation separately. Never downgrade a shared runner, edit a registry value to imitate the minimum or use a compatibility runtime/VM boot as execution evidence. Minimum-runtime machines must be isolated and independently provisioned; complete supported OS/image/patch/security evidence remains mandatory.

`eng/test-runtime-lane.ps1` takes one declared lane, an explicit already built consumer project and an owned output directory. It preflights the physical host and Framework installation, runs the full unfiltered test project at the selected process bitness, and validates the resulting same-process observation. It never installs a runtime, rebuilds/retargets a consumer, chooses an emulator or infers fallback. The caller must have built the exact fallback consumer when that lane is requested. Wrong-host/minimum observations reject before or after execution rather than becoming skipped tests.

Each invocation requires fresh report paths. Existing reports or input aliases reject without overwriting evidence. Platform applicability is explicit:

| Surface | Applicable host | Required observation |
| --- | --- | --- |
| Managed SDK contracts | All 22 lanes | Actual runtime, loaded normal/fallback assets and complete reviewed package-consumer tests |
| Native workers and optional engines | Declared supported native OS/RID with provisioned sandbox/assets | Actual isolated engine execution; a missing prerequisite blocks its lane |
| COM automation | Windows Framework x86/x64 | Registered native/VBScript consumer and lifecycle evidence, separately from portable interface tests |
| WinForms/WPF samples | Windows supported UI/runtime combinations | Actual UI navigation/focus/printing and accessibility evidence |
| Browser sample | Supported modern server runtimes and browser hosts | Actual authenticated browser/client behavior |

The generic contract project does not qualify those separate host integrations. Platform-specific suites require their own complete inventories and reports; this table does not waive a required runtime or feature. Linux Docker containers cannot provide Windows Framework execution. A Windows-container lane requires a compatible Windows host and independently verified actual installed Framework version; an image tag or successful container boot is insufficient.

Source mode records identity consistency only. It does not establish full test coverage, exact package restoration or trusted-host provenance. Package mode additionally requires a reviewed complete test-ID/name inventory, exact stable-version package manifest, every feed artifact SHA-256, a consumer dependency graph showing package references, and exact loaded DLL hashes matching the selected `lib/<tfm>/` assets inside the packages. The package manifest contains `schemaVersion`, `packageVersion`, `packages` (`id`, `version`, `file`, `sha256`) and `consumerDependencyGraph` (`file`, `sha256`); paths are relative to its artifact directory. The reviewed inventory has purpose `reviewed-runtime-test-inventory`, schemaVersion 1 and a `tests` array of unique `testId` and exact `testName` pairs; truncated theory display names may repeat, but their test and execution IDs must be distinct. No source/project-reference report is promoted to package evidence.

These checks establish structural consistency of supplied evidence. Reports still need a trusted execution/provenance chain and complete functional, fidelity, security, resource, concurrency and consumer suites. A report can never attest its own physical host. The checker always retains `productionQualified:false`; it does not change the release switch or create/publish packages. Synthetic checker-unit fixtures are explicitly labeled and are not actual runtime or qualification evidence.

Current source CI covers six native modern hosts and current Framework x86/x64. Exact stable packages, actual minimum Framework 4.7.2 hosts, reviewed complete package-consumer inventories and complete production suites remain missing. The task environment also lacks required local Landlock isolation for five native source classes; selected local source tests do not replace those lanes. No required lane, suite, feature or original production gate is removed or weakened.

## Windows PC container preflight

With PowerShell 7.2+ and Docker Desktop installed on a compatible Windows PC, select **Switch to Windows containers** in Docker Desktop. From this branch's repository directory, run `pwsh -NoProfile -File eng/probe-framework-container.ps1 -StartDockerDesktop -OutputDirectory artifacts/framework472-probe`. The script can start an installed Docker Desktop; it does not install software, enable Windows features, switch engines or modify the host Framework. Hyper-V isolation must already be available. Pulling the Server Core image can download several gigabytes.

The launcher uses the local named-pipe daemon explicitly, preserving Docker credentials and restoring endpoint selectors afterwards. It pulls the explicit official Server Core 2019 candidate, resolves and records its exact digest, then starts a uniquely named Hyper-V container with no network, mounts or published ports. Actual 32-bit and 64-bit Windows PowerShell children inspect their installed Framework registry release, CLR, core-library version and hash. A newer Framework image rejects. The script removes only its own container and retains the pulled image. It never downgrades Framework or edits a version key.

The current official Framework runtime manifest advertises newer runtime images; a Framework SDK tag is not evidence of 4.7.2. Server Core 2019 is a candidate, subject to the live checks. This launcher has been parsed and its Linux-host rejection exercised here; its Windows/image/Hyper-V execution remains unqualified. Its report is a preflight only: it executes no SDK tests, restores no packages and cannot complete #90. The resulting image would still need explicit offline test/native-tool assets and full runtime/package consumer provisioning. See the [official Framework container sources](https://github.com/microsoft/dotnet-framework-docker) and [Windows container compatibility guidance](https://learn.microsoft.com/virtualization/windowscontainers/deploy-containers/version-compatibility).

## Offline Windows VM source execution

A Windows guest VM is another minimum-runtime host option. It does not require Docker's Windows-container engine: a Linux container can supervise a separate Windows VM, but the Linux container itself never supplies Framework execution. Preserve the original VM disk and use a separately owned copy. Record OS/image/provisioning provenance and whether execution uses hardware virtualization or software emulation. Neither booting the VM nor reusing another product's earlier test results qualifies Fluent.Pdf.

The Windows x64 source CI job prepares and retains `framework-source-bundle-win-x64` after compilation and API checks, before test execution. This preserves reproducible inputs when any subsequent suite fails; an uploaded bundle is not passing test evidence. Both the ordinary source suite and the offline launcher remain required checks. [new-framework-test-bundle.ps1](../eng/new-framework-test-bundle.ps1) requires a clean commit, matching native fixture hashes, the pinned independent validator, an explicit Java distribution and the signature-verified Microsoft.TestPlatform 18.11.0 package (SHA-256 `0845b73d09563c5d7c4c19ad8d55db52df427aa395140437f546d4487900e4f1`). It copies source test binaries, native fixtures for both architectures, Java and dependency notices, then hashes every input. The test platform is an analysis-only tool, never an SDK dependency. Its full package includes upstream license/notices. See the [official standalone runner guide](https://github.com/microsoft/vstest/blob/main/docs/quickstart.md).

Transfer the artifact from the exact reviewed CI commit into an isolated Windows guest with actual Framework 4.7.2. Preserve the downloaded artifact hash and `bundle.json`. From Windows PowerShell 5.1, run each architecture using fresh directories:

```powershell
.\run-framework-bundle.ps1 -Architecture x64 -RequireFramework472 -WorkspaceDirectory C:\pdf-work-x64 -OutputDirectory C:\pdf-results-x64
.\run-framework-bundle.ps1 -Architecture x86 -RequireFramework472 -WorkspaceDirectory C:\pdf-work-x86 -OutputDirectory C:\pdf-results-x86
```

The bundle checks file hashes and rejects additional files before creating a private workspace. The original inputs remain unchanged when tests create fixture outputs. The [offline runner](../eng/run-framework-contracts.ps1) needs no modern SDK or PowerShell installation in the guest. It uses the standalone Framework test platform with no test filter or implicit JIT override, checks actual installed and test-process identities, and fails on any missing, failed or skipped test. Its external deadline terminates only the owned test process tree and retains logs, TRX and `framework-execution.json` even on failure. Synthetic launcher regression reports are explicitly separate from actual SDK execution.

Copy each result directory and its workspace's `artifacts/contracts` back to the analysis host. Run `eng/check-runtime-evidence.py --lane win-x64-framework472 --trx <results>/runtime-contracts.trx --mode source --output <fresh-report>.json` (use `win-x86-framework472` for x86). The bundle origin, input hashes and actual test process must agree. These source results do not qualify exact packages, trusted-host provenance, full production suites or emulated performance. The 22-lane inventory and publication gates remain unchanged.
