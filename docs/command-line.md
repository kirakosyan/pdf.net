# Command-line and batch automation

FP-083 has an original optional source application in `apps/Fluent.Pdf.Cli`. It consumes the public Core and Formats APIs; it has no native/browser/model/UI provider or runtime package dependency beyond those existing assemblies and the .NET runtime. The executable targets .NET 8 and .NET 10 on Windows, Linux and macOS, including x64/ARM64 source lanes. The library's four target contracts remain independent. Legacy Framework CLI hosting, complete provider bindings and exact final application/package distribution remain mandatory additional work; no package is produced or published by this source profile.

Run the built application with `dotnet apps/Fluent.Pdf.Cli/bin/Release/net10.0/fluent-pdf.dll --help`. The help channel is stderr. `--version` writes machine-readable actual runtime, OS, architecture and loaded SDK target identity to stdout. Runtime and source observations do not establish production qualification.

```sh
dotnet fluent-pdf.dll text --input input.pdf --output captured.txt --view raw
dotnet fluent-pdf.dll select --input input.pdf --output selected.pdf --pages 2,1
dotnet fluent-pdf.dll rewrite --input - --output -
dotnet fluent-pdf.dll preflight --input input.pdf --output preflight.json
dotnet fluent-pdf.dll convert --input vector.pdf --output vector.svg --target Svg
dotnet fluent-pdf.dll decrypt --input encrypted.pdf --output plain.pdf --password-file protected-password
dotnet fluent-pdf.dll batch --config batch.json
```

`text` distinguishes raw, semantic and geometric layout views under the shared extraction contracts; pages are separated by a form-feed character. `select` uses the existing one-based ordered range syntax, including duplicates, descending ranges, `all`, `last`, `odd` and `even`. Organization retains its strict navigation/field/tag limitations. Full PDF rewrites and page selection require `--allow-signature-invalidation` when signatures are present. Nothing authenticates or decrypts ordinary input implicitly. `decrypt` selects the existing password handler explicitly and does not opt into legacy ciphers. `preflight` remains passive; it is not complete conformance validation or automatic remediation. `detect` reports content family separately from validation. `formats` lists the SDK's exact nine-profile matrix and separately declares the CLI's two provider-free vector targets, `Svg` and `StaticEps`. Requested raster targets fail with `CLI.RendererRequired`; there is no engine discovery, runtime download or fixture fallback. Unsupported vector content rejects rather than substituting blank/raster output.

PDF/UTF-8/JSON command data goes only to stdout or the explicit output file. Diagnostics go only to stderr as schema-one JSON lines. They retain stable codes and non-sensitive caller job IDs, without exception text, source text, file paths, argument values or credential bytes. Diagnostic codes from all shared operation reports are collected, with a fatal 64-code command ceiling rather than silent loss. A processing failure emits no staged data. Pipe transfer can fail after some bytes have reached a consumer; that result returns failure and `stdout-may-be-partial`. Redirected output uses borrowed raw OS handles because the console's text stream can suppress broken-pipe errors. Callers must drain both process channels.

| Exit code | Meaning |
| --- | --- |
| 0 | Requested operation succeeded |
| 1 | Other redacted application failure |
| 2 | Invalid arguments/configuration or unsafe password-file permissions |
| 3 | Invalid/unsupported PDF, authentication, signature authority or unavailable target/provider |
| 4 | Resource limit or timeout |
| 5 | Input/output, destination publication or owned temporary cleanup failure |
| 6 | Batch completed with one or more failed jobs |
| 130 | Global cancellation requested |

Defaults are 16 MiB input and output, 128 MiB expanded bytes, 250,000 objects, 16 million pixels, 64 diagnostics and a 30-second command deadline. Direct flags can set input/output limits up to 64 MiB and a deadline from 1 to 300,000 milliseconds. Input capture, individual SDK operations and output staging have explicit finite bounds; each SDK operation receives the same immutable policy, while one linked command deadline spans the phases. These are logical quotas, not a hard process RSS limit. File/OS completion and shared SDK checkpoints remain cooperative. No SDK operation or provider callback is abandoned.

The CLI owns its process, standard handles, staging and input admission. Blocking console/pipe/path admission is supervised before any SDK operation starts. A canceled admission retains its private read buffer/handle until completion or process exit and reports `input-released-on-process-exit`; it never transfers a partial input to the SDK. Configuration admission has a separate five-second ceiling. A blocked standard-output transfer similarly owns its private copy until completion/exit. These process-lifetime rules are not an embeddable library API. Full opaque-filesystem, console/signal-host, backpressure, concurrency and endurance qualification remains mandatory.

Processing stages input/output in bounded private managed buffers. Before file publication, the application creates only a random owned temporary file in the destination directory, with mode 0600 on Unix or an explicit user/System/Administrators ACL on Windows. It flushes and closes that file, checks cancellation, then renames it into place. Existing destinations are retained unless `--overwrite` is explicit. Every new output is private. Replacement intentionally adopts the new private permissions, including when an existing destination was readable by a group, web server or inherited Windows ACL. After successful publication, callers must explicitly grant any desired sharing permissions using their OS tools. The CLI does not infer or widen access from a destination path or prior file. A failed operation removes only its own temporary file; cleanup failures retain an opaque temporary basename in the result for recovery. Callers must serialize destination/directory maintenance and protect their filesystem namespace. This is not an adversarial-filesystem sandbox or secure erasure guarantee.

Password material is accepted only from `--password-file`, never from an argument, environment variable, JSON scalar or diagnostic. The file contains at most 4096 exact standard-prepared bytes, with no implicit trimming, encoding conversion or Unicode password preparation. Unix rejects group/other/special permissions; Windows requires the current owner and allow entries limited to that user, System and Administrators. Final symlink/reparse password files reject, and permission checks use the opened handle. Managed temporary password arrays and the SDK's owned password copy are cleared after use. Complete host/filesystem-race and memory-erasure qualification is not claimed.

`run --config` accepts exactly one job; `batch --config` accepts one to 256 jobs and one to four workers. Configuration is UTF-8 JSON at most 1 MiB/depth 16, with duplicate and unknown keys rejected. Root fields are `schemaVersion` (required 1), `jobs`, `parallelism`, `maximumInputBytes`, `maximumOutputBytes`, `timeoutMilliseconds`, `report` and `overwriteReport`. A job accepts `id`, `operation`, `input`, `output`, `pages`, `view`, `target`, `passwordFile`, `overwrite` and `allowSignatureInvalidation`. IDs are required non-sensitive ASCII letters/digits/underscore/hyphen, at most 64 characters. Option applicability is strict. All paths resolve relative to the configuration file. The [batch example](../examples/cli/batch.json) needs a caller-provisioned `input.pdf` beside it.

Batch jobs cannot use standard input/output. Duplicate IDs, duplicate output paths and output/input/password/report collisions reject before scheduling; path keys conservatively ignore case and canonical Unicode spelling on every host. Physical namespace aliases still require caller control. Dependency graphs through files are not inferred. Batch requires an explicit result-report path. Existing reports need explicit `overwriteReport`. Successful job outputs remain published when siblings fail. Every job, including queued cancellation, retains its ordered exit code, publication and cleanup outcome. The aggregate report is published atomically before console diagnostics, and batch stdout carries that JSON manifest rather than PDF bytes. Report/publication failures return an I/O failure; full crash/power-loss and filesystem durability qualification remains open.

`eng/test-cli.py` runs actual built processes, protected inputs, bounded partial batches, timeout cancellation, binary pipe separation, closed pipes and output preservation on both runtimes. The original encrypted fixture is produced by an independent analysis engine with a public test password. `eng/verify-cli-fixtures.py` checks PDF Unicode/order through two independent readers, exact original vector pixels for SVG/EPS, and preflight source binding. Analysis tools are not runtime dependencies. [Exact clean-source/runtime evidence](evidence/FP-083-source.json) binds application code, actual process groups, independent outputs and the separate host-consumer correction. Complete corpus/provider/host/security/performance/fuzzing and final-package gates remain mandatory; the requirement stays planned.

Actual source consumers passed both runtimes across all six Windows/Linux/macOS x64/ARM64 hosts using identical product code: 13 process groups per Windows runtime and 14 per POSIX runtime, including its applicable FIFO case, totaling 164 groups with zero failures/skips in those passing observations. The Windows consumer needed explicit UTF-8 file decoding; product behavior was unchanged. The evidence binds the earlier successful macOS-x64 job separately from the other five corrected-consumer jobs and does not infer final-package or full host qualification.
