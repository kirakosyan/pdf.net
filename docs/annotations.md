# Annotations and appearance streams

FP-019 has an original managed source implementation with the same API on all four target frameworks. Production qualification remains pending. Inspection never runs document actions, media or file content. The core includes no annotation renderer, media engine or implicit resource download.

`PdfAnnotation.Create` captures a detached normal Form appearance, native page-coordinate rectangle, document-unique authored identifier, standard subtype properties and Unicode metadata. Comments, highlights, underlines, strikeouts, squiggles, ink, stamps, squares/circles, lines, polygons/polylines, free text, carets, file attachments and rich media have explicit contracts. Required coordinate arrays, geometry extent, precision, appearance bounds, attachment data and media identities are validated. The advanced property contract has an explicit version floor (default 1.7); known features can raise it. Rich media requires PDF 2.0. The dictionary API does not infer arbitrary future extensions or regenerate custom artwork.

`CreateMarkup` generates original vector appearances for text-note icons, shapes, ink, carets and text markup. It accepts explicit DeviceGray/RGB/CMYK color, stroke width and opacity. Highlights use Multiply within their appearance; annotation CA metadata is not applied again during flattening. QuadPoints use upper-left, upper-right, lower-left, lower-right order in this generated profile. Appearance drawing is clipped by the explicit rectangle; callers provide room for strokes. Additional icon, cloudy border, dash, ending, fill and other styles require a custom appearance and fail explicitly in this factory. A squiggle is bounded to 4096 segments per quad. Stamps and media have explicit custom/poster appearances.

`CreateFreeText` embeds already shaped glyphs, exact logical Contents/ActualText and font resources in the normal appearance. Font size and geometry are in native page units. A conservative global font-box envelope, including shaping offsets and paragraph positions, rejects overflow. Explicit clipping additionally requires permissive loss handling. This is a fixed shaped appearance; later arbitrary live text editing, default-font substitution and automatic appearance regeneration are separate profiles. No font/shaping provider is discovered implicitly.

`PdfAnnotationMetadata` retains authors, contents, subjects, offset-bearing creation/modification dates, states/models and stable forward reply identifiers. New strings use UTF-16BE. Original supported legacy/Unicode text strings decode without a platform code page; original dictionary bytes remain available. Source date/state strings are retained without normalization. Metadata fields supplied through the explicit metadata contract take precedence over additional properties.

`PdfAnnotations.Add` stages a finite batch of at most 10,000 annotations in one shared operation. New identifiers are document-unique; existing page-scoped duplicate names remain intact. A name-based reply requires an unambiguous indirect target. `PdfAnnotationSet.Inspect` returns immutable original dictionaries, indices, page ownership, text metadata and indirect identities after caller disposal. Unknown subtypes remain inspectable with a diagnostic. Replies are checked for cycles and bounded depth; popups require reciprocal same-page ownership.

`Update` preserves every unspecified dictionary entry and the existing identity, relationships and alternate appearances. Geometry edits require corresponding subtype coordinate changes where necessary. Generic advanced patches require at least PDF 1.7. `SetReply` edits a captured identity relationship; `AddPopup` creates reciprocal parent/popup references without an appearance stream. `ImportTo` stages an explicit selection into a target page, preserving indirect sharing/cycles, appearance resources and exact payload bytes. Missing ancestors, other unmapped page targets, identifier collisions, widgets without their field ownership, optional-content and structure relationships require their explicit profiles. Source and target streams remain caller-owned.

File attachment authoring requires an actual embedded stream and file specification. The Video/Sound rich-media authoring profile requires sorted named assets, configurations, instances and exact shared file-specification identities; materialization creates real indirect file/configuration/instance references and unique annotation settings. A MIME subtype and poster appearance are explicit. The SDK packages opaque caller-selected media bytes; it does not decode or validate media containers or play them. Imported media dictionaries remain passive and retain unsupported data; authored 3D/script/view graphs require additional profiles. Tests include an original valid two-sample PCM WAVE payload.

`Delete` removes selected annotation entries and, by default, reply/popup descendants. It clears reciprocal popup ownership. Deleting structured source annotations requires a preservation profile. Objects and historical/unused bytes may remain; deletion and flattening are not secure erasure.

`Flatten` selects explicit screen or print visibility, paints the normal appearance and removes selected interactivity. It transforms the appearance BBox by its Matrix, maps that transformed box to Rect, and invokes the original Form with its own matrix/resources/encoded bytes. Balanced original page content is retained between separate q/Q streams so its ending state cannot affect the overlay. Appearance-state dictionaries require a matching AS name. Hidden/NoView/Print have explicit rules; Invisible does not hide a recognized standard subtype. Popup windows are removed without painting. Missing appearances, widgets, NoZoom/NoRotate/ToggleNoView, annotation-level blend overrides, page transparency groups, optional content and structure require explicit profiles. Rich-media static conversion requires both an explicit poster-only choice and permissive loss handling. No appearance is silently synthesized and no payload is executed. PDF path saving remains atomic through the existing writer; full signed rewrites require explicit invalidation permission.

## Explicit XFDF interchange profile

`WriteXfdf` and `ReadXfdf` support common annotation metadata in the standard XFDF namespace plus a mandatory original owned-graph extension. The extension retains exact encoded appearances/payloads, unknown dictionary data, indirect sharing, cycles, page-coordinate geometry, replies and popup references. It exports annotation-owned graphs and blank page frames; original page body content is not exported. Document/catalog, widget/field, optional-content, structure and developer-extension ownership are rejected rather than copied implicitly. Named local actions require their destination import profile.

Both directions have a 16 MiB XML and 10,000-page ceiling in addition to operation budgets. XML parsing prohibits DTDs and external entities, bounds characters/depth, rejects duplicate/missing object identities and validates standard metadata against the retained graph. Whitespace, CR/LF and Unicode metadata round-trip exactly. Unsupported standard XML styles or external XFDF without the owned graph produce an explicit profile/appearance-provider diagnostic. This is not general XFDF 3.0 conformance or interoperability qualification; consumers that ignore the extension cannot reconstruct its exact custom appearances. Stream output may be partial after failure and preserves caller ownership.

## Evidence and remaining qualification

Source tests exercise all authored subtypes, original generated markup, shaped text/fonts, valid embedded PCM bytes, metadata/dates/states, forward replies/popups, source disposal, imports, transformed appearance geometry, visibility, signed/structured policies, XML round trips, cancellation and resource limits. C# and VB examples emit actual annotated PDFs. Neutral primary-standard fact IDs and capture hashes are retained separately from external raw research.

Full viewer/conformance/semantic/visual and external XFDF corpora, additional compositing/view-dependent/ownership/media/regeneration profiles, actual minimum Framework runtimes, final packages and all security/fuzz/concurrency/endurance gates remain mandatory. No requirement status is promoted to qualified. NuGet candidate creation and public publication remain blocked.
