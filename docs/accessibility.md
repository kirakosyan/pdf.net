# Logical structure and accessibility

FP-067 has a managed source-validation profile. Complete PDF/UA-1 and PDF/UA-2 semantics, role/namespace/attribute profiles, authoring/edit/merge fidelity, screen-reader/human review, all required runtimes/packages and every production gate remain mandatory. SDK candidate creation and NuGet publication remain blocked.

`PdfAccessibility.Author` writes an explicit `PdfStructurePlan` over actual existing page/Form MCIDs and annotations. `PdfStructureElement` captures a standard role, ordered children/content, language, descriptions, replacement text, optional ID and explicit table attributes. `PdfStructureContent.MarkedContent` selects an existing page MCID or explicitly identified Form stream; `Annotation` selects an exact source annotation. No semantic reading order, image description, table header or form meaning is inferred from geometry. Figures, formulas and forms require meaningful author-supplied alternative or replacement text. Decorative content uses the existing explicit Artifact marked-content operators.

The plan has one Document root. Every actual structural MCID needs exactly one owner. A fresh root, element parent links, page/Form parent arrays, annotation parent keys, ID name tree and explicit table attributes are written together. Header IDs must identify TH elements; header relationships must be acyclic. Links and widgets need Link and Form owners. Repeated Forms with their own MCIDs reject, as does combining whole-Form ownership with inner MCID ownership. Repeated untagged Forms may be covered by distinct outer page sequences. PDF2 authoring supplies an explicit standard structure namespace and raises the PDF version floor. Full role-map/namespace, appearance-stream and additional metadata profiles remain mandatory pending scope.

`Inspect` returns the normalized immutable source, exact element IDs/raw dictionaries/child order, logical content associations and bounded automated findings. It validates parent-tree ordering/ranges, unique owner keys, MCID coverage, page/Form/annotation ownership and balanced/cyclic references. It inventories unmarked painting and missing source semantics. Its checks are deliberately incomplete: an empty source-finding inventory would not establish conformance. `HumanReviewRequired` is always true. Full class-map/attribute inheritance, inherited form descriptions, complex tables, language/Unicode/font semantics and reading-order correctness require complete independent and human validation.

`Remediate` takes an inspection source and exact element ID. It changes explicitly supplied role/language/descriptions and optionally applies an exact permutation of all existing children. Null fields retain source values; identities, content associations, unknown metadata and parent-tree links survive. Element revisions increment so prior attached attributes can be identified as stale. Role changes with attached attributes or table/annotation semantic ownership reject until a complete remediation profile is supplied. Full replacement of an existing structure requires `replaceExisting: true` and reports semantic loss; strict mode rejects that loss. Complete tag-aware content editing, arbitrary reparenting, role/namespace/class-map and edit/merge profiles remain mandatory.

Inspection, content/filter traversal, Form recursion, semantic binding, number/name-tree assembly, staged graph edits and writing share one mandatory operation context. Root object/depth/input/expansion/time/output budgets apply. Source models remain unchanged on failure; edited models serialize privately before exposure. Signature invalidation still requires the existing explicit organization choice. Caller input/output ownership and atomic saves use the ordinary shared contracts. Source input is passive: no annotation action, script, external resource, font or model is executed or discovered.

`PdfAccessibility.Validate` delegates complete UA-1/UA-2 checking to an explicit `IPdfAccessibilityValidator`. Results bind the exact profile and lowercase source SHA256. A provider cannot return a different document/profile or hide latched cancellation/limits. `PdfAccessibilityHumanReview` separately records an explicit matching profile/digest, reviewer/report identity, reading-order observation and semantic-review observation. Automated success never supplies or approves human review, and a supplied false observation stays false.

The optional `Fluent.Pdf.Compliance.VeraPdfAccessibilityReportValidator` parses reports from an explicitly supplied offline host using pinned veraPDF 1.28.2. It creates no process/file or implicit engine installation. It requires complete exact-engine/profile/job/batch/rule/check totals, rejects wrong/contradictory/truncated reports and disables XML DTDs/resolvers. UA-2 uses the engine's complete `PDF/UA-2 + Tagged PDF validation profile`. Its shared bounded report parser also preserves existing archival validation behavior. Supervised host provisioning/isolation and complete qualification remain obligations.

Authoring does not add identification metadata or fabricate conformance. Callers can explicitly set document title, XMP UA identification/revision and viewer preferences through existing metadata/presentation contracts, then validate exact serialized bytes. Original figure fixtures with explicit descriptions/language/title/identification pass independent automated UA1/UA2 checks; unprepared fixtures correctly fail. No human or screen-reader review is claimed. These finite fixtures do not qualify complete accessibility, reconstruction, arbitrary documents or final SDK packages.

All core/optional compliance contracts target net472, netstandard2.0, net8.0 and net10.0. C# and VB `TagPdf` consumers execute through public contracts. Independent readers inspect original MCID/parent associations, Form/annotation references, PDF2 namespaces and exact unchanged pixels through reading-order edits. See [source evidence](evidence/FP-067-source.json), [independent observations](evidence/FP-067-independent.json), [production gates](production-quality.md) and [platforms](platforms.md).

A RoleMap entry whose key is already a standard role produces `Accessibility.RoleMap` and is ignored for effective semantics. It does not block inspection or explicit remediation. Repeated elements using one unmapped custom role produce a single `Accessibility.RoleMapping` finding for that distinct role, preserving the bounded finding inventory for other problems. Cyclic mappings and malformed custom mappings still reject.
