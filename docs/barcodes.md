# Barcode, QR and payment workflows

`PdfBarcodes.Generate(text, independentDecoder, options)` returns a symbol only after an explicitly configured independent decoder reproduces the complete exact Unicode text, symbology and error-correction level from its actual canonical opaque pixels. Missing, unavailable, mismatched or failed decoding rejects before a drawing returns. `Fluent.Pdf.Ocr.ZxingBarcodeDecoder` is an optional concrete decoder pinned to ZXing.Net0.16.11; the managed core contains original encoders and retains its dependency boundary. Decoder identity is explicit caller configuration, and providers must be independently implemented. Identity strings alone do not prove independence or production qualification.

Generation supports QR Model2 versions1–40, byte mode with UTF8 ECI26, all levelsL/M/Q/H, deterministic standard block/error correction/layout and lowest-penalty mask selection. Version zero chooses the smallest fitting version; an explicit version never truncates or substitutes text. Quiet zones are at least four modules. Code128 generation is the finite code-setB profile:1–256 printable ASCII32–126 characters, modulo103 checksum, at least ten quiet modules and explicit bar height. It adds no FNC/GS1 or code-set switching. Arbitrary binary QR payloads, other symbol families and implicit text normalization are outside these generation profiles.

Each accepted `PdfBarcodeSymbol` contains a detached device-gray vector `Drawing`, including the white quiet zone, its module dimensions, actual QR version/mask, exact verified raster and completed report. `OpenVerificationPixels` opens a detached read-only Gray8 view of the checked pixels. Place the drawing with `PdfCanvas.DrawDrawing`, source bounds `(0,0,symbol.Width,symbol.Height)` and an explicit destination using aspect-preserving fit. Physical print size, transformations, clipping, substrate/contrast and scanner conditions affect readability; final PDF/render/print workflows require their own independent decoding. The source checks include actual vector PDF placement through compiled C# and VB examples and decoding after two unrelated PDF readers.

`Detect` accepts an explicitly captured `PdfOcrRaster`; `DetectPage` renders a selected PDF page/region with an explicitly registered renderer and the same shared budget/context. Its default is opaque96DPI. Explicit rendering requires isotropic integer72–600DPI, and the provider's raster ceiling still applies. The supplied optional decoder supports one symbol per requested image/region, rotations, inversion and QR correction. Request separate explicit regions for several codes. It caps inputs at1048576 pixels and32768 per dimension and precharges conservative managed workspace before its bounded synchronous call. It checks cancellation/deadline before/after the engine and in its own capture loops; hard preemption of that managed engine call is not claimed.

Detection text is decoded Unicode. It is not automatically interpreted as a URI, command or payment instruction, and it is not a claim about the original byte encoding of arbitrary input. Detector landmarks are QR finder/alignment centers or Code128 scan-line endpoints, rather than symbol outline corners. Standalone results use top-left image pixels. Page results explicitly carry the page index and map landmarks to native PDF user coordinates through exact crop, region, rotation and UserUnit geometry. Transparent BGRA samples reject unless explicitly composited first. Source/frame/provider failures retain stable `Barcode.*` diagnostics; raw payloads are absent from diagnostics.

`PdfSepaCreditTransfer` validates a canonical twelve-line EPC002, charset1/UTF8, SCT/EUR payment profile. It requires explicit BIC8/BIC11 syntax, country-length IBAN and ISO11649 RF modulo97 checks, positive exact EUR minor units, literal bounded fields and mutually exclusive structured/unstructured remittance. Supported IBAN country-length records are the explicit catalog in the implementation; unknown countries reject. This source profile requires a BIC, even where a broader EPC workflow might omit it. Its maximum330 complete UTF8 bytes reserve explicit ECI26 within QR version13M. It rejects other editions, encodings and noncanonical layouts without guessing. Bank existence, purpose-code registry validity, account ownership, payment authority and bank acceptance are separate checks.

`FromInvoice` uses the immutable EUR invoice's literal seller/identifier and reconciled gross/due amount, and rejects unsupported currencies, precision, zero/out-of-range amounts and overlong fields. It never converts currency, infers discounts/prepayments, truncates identifiers or submits a transfer. `GeneratePayment` requires independent exact decoding at levelM. `Parse` validates the same exact canonical profile before data is accepted.

Every job uses finite input/expanded/pixel/object/depth/output/deadline limits. Provider pixel leases expire at return. Independent jobs have separate readers, buffers and reports; no credentials, payloads, decoder settings or document caches are global. Stream/file output uses the existing explicit canvas/document APIs and their ownership/atomic save contracts.

The dependency decisions, exact package/runtime assets and licenses are recorded in [barcode notices](../third-party/barcodes/README.md). Actual minimum Framework, all engine/runtime/RID lanes, broad multi-code/general symbology/payment profiles, multilingual/damage/printing/scanner/fuzz/resource/concurrency/endurance corpora, complete independent acceptance and final package consumers remain mandatory. These source profiles do not complete FP-078 production qualification.
