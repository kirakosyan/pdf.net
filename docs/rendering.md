# Page rendering source profile

`PdfRendering.RenderPage` requires an explicit `IPdfPageRenderer`. The managed core remains independent of native engines, desktop sessions and platform graphics types. `Fluent.Pdf.Rendering` contains a candidate `IsolatedPdfRenderer` adapter for the pinned PDFium 153.0.7999.0 build. This is source integration, not adoption or production qualification of that engine.

The input is an immutable snapshot. An unchanged imported document retains its exact original bytes, including incremental history. Authored or changed snapshots are privately prepared using the same operation context. Preparation can invalidate signatures in that private preview; rendering does not save over the original, verify signatures or declare their validity. Rasterization never intentionally executes document JavaScript, actions, attachments, network resources, form calculations or file submissions. The selected engine assets contain no V8/JavaScript or XFA build features. Form-fill callbacks have no action/network platform.

## Coordinates and samples

The default region is the effective CropBox after native page rotation and UserUnit. Region coordinates use a displayed top-left origin and physical points, matching `PdfPageGeometry.UserToDisplay`. A region must be positive and entirely inside that box. Each full-page dimension is `ceil(physicalPoints * requestedDpi / 72)`. The resulting full-page grid fits the complete displayed box; effective DPI is reported separately for each axis. Regions snap outward on this same grid. `Request.Region`, `X`, `Y`, full dimensions and effective DPI make every rounding decision observable. Rendering a region uses the same scale and pixel phase as that window of a full-page render, without allocating the full-page raster.

`PdfRaster.OpenSamples` returns an independent read-only view of tightly packed, top-down BGRA bytes. Alpha is straight, not premultiplied. Fully transparent samples have zero RGB. `backgroundRgb: null` requests transparency; an explicit `0xRRGGBB` matte requests opaque output. Device RGB is the default. Device gray retains four bytes per pixel with equal color channels and requires a gray matte. This is device-color rendering, not proof of ICC/output-intent/spot-color fidelity or a proofing workflow. The result is raw samples; image encoders and multipage output belong to their respective requirements.

Annotation rendering includes existing normal widget appearances. `annotations: false` excludes both annotation and widget painting. Print intent selects print visibility and native optional-content print usage. The adapter applies widget visibility flags in its private worker before form-page-view creation because candidate form-fill drawing does not consistently honor the print flag. This does not alter the caller document. Source layer defaults remain native defaults; alternate layer selection is an explicit document/layer operation. The adapter disables machine-font discovery and rejects nonstandard unembedded fonts. Standard 14 fonts use the engine's bundled substitutes; embedded and Type 3 fonts remain document resources.

## Explicit boundaries

The candidate adapter rejects XFA, PDF 2.0/extensions, external stream files, nonstandard unembedded fonts, unknown content operators and source `NeedAppearances` when annotations are requested. Non-link/non-popup annotations require explicit normal appearances; implicit viewer appearance generation is outside this profile. Page and nested Form content is parsed under the same context before native execution. Existing normal appearances are painted without running field scripts or calculation actions. Additional appearance, Type 3/inline-resource, malformed embedded font, color-management and extension profiles still require complete validation. Unsupported requested profiles produce typed failures in both processing modes; the adapter does not silently select another renderer.

Input, output, pixels, graph visits, depth and native memory/execution are bounded by one context. Samples and IPC copies are charged before allocation. The existing worker supplies a fresh private staging directory, exact asset hashes, OS isolation, parent-death cleanup, deadlines and cancellation. There is no in-process fallback or request retry after engine execution. A caller provides an explicit offline `NativeWorkerOptions` deployment with the worker, original bridge and exact native engine asset. No runtime download occurs. The optional project is non-packable, and all SDK packing/publication gates remain blocked.

`third-party/rendering/components.json` records six candidate assets, container hashes, native hashes and complete upstream notice inventories. CI explicitly downloads and verifies those assets before building the original bridge; this is provisioning for tests, not SDK runtime behavior. The adapter requires the exact inventoried native engine size and SHA-256; a caller-supplied version label alone is insufficient. All engine bytes remain unchanged. On macOS, only the original bridge receives a private loader-relative dependency and ad-hoc signature. Engine and bridge hashes are retained. The complete notices are retained with each CI asset and must accompany any approved redistribution. No native engine binary is committed or packaged. Engine source/build provenance, license/security review, supported minimum OS and transitive platform dependencies remain production blockers. Framework x86 callers use a 64-bit OS worker; no x86 engine is implied.

Source tests cover integer-grid geometry, output/worker budgets, cancellation, borrowed streams, exact native pixels, crop/rotation/UserUnit, alpha/matte/gray, existing widget appearances and print visibility. Independent probes and per-platform source CI do not replace the required large independent-renderer corpus, visual/color/semantic metrics, concurrency, fuzzing, endurance, actual minimum runtimes and exact final-package consumers. FP-040 remains planned until reviewed implementation and complete qualification evidence satisfy its full acceptance criteria.
