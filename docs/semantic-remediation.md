# Semantic remediation and review ledger

FP-101 adds source-level review contracts over the existing [structure authoring and inspection](accessibility.md). It remains planned, not production qualified. All core APIs target net472, netstandard2.0, net8.0 and net10.0 without new package dependencies. Candidate creation and publication remain blocked.

`PdfSemanticSuggestion` captures a caller-proposed element change, custom role map or complete structure plan. An element suggestion can include a standard role, language, alternative/replacement text and an exact permutation of existing children. Its reason records why the proposal exists, including any inference by an upstream layout/table/model component. The SDK does not invent descriptions or certify inferred reading order. Suggestions and their copied child-order arrays are immutable.

`PdfAccessibility.PrepareReview` captures bounded source bytes, checks structure passively and binds an ordered inventory of at most 128 distinct suggestions to the exact SHA-256. It returns the original automated findings and always reports `HumanReviewRequired`. Preparation changes no source bytes and accepts no suggestion. A complete `PdfStructurePlan` must stand alone because authoring creates new structure identities; it reuses explicit headings, lists, table cells/header IDs, existing MCIDs and annotation associations. Existing-structure replacement still requires its explicit loss choice and applicable permissive policy.

`ApplyReview` and `ApplyReviewFile` require the same exact bytes and explicit `PdfSemanticReviewDecision` records. Each decision has a suggestion ID, accept/reject value, reviewer and note. These are caller assertions, not authenticated identities or proof that a human used a screen reader. Unknown/duplicate decisions reject. The plan defines application order. Unmentioned proposals remain pending; rejected and pending proposals do not change bytes. If none is accepted, the output is an exact copy of the source.

Each accepted element fix uses the existing identity-preserving remediation path. Each accepted complete plan uses the existing authoring rules, including unique MCID coverage, parent associations, meaningful figure/form/formula descriptions, table header references and cycle rejection. After every accepted fix, the entire structure is inspected, the PDF is serialized privately and the serialized result is reparsed and inspected again. Invalid later fixes discard earlier staged changes; no caller bytes or destination file are committed. File output is atomic; borrowed stream I/O failure can still leave partial external output. Signatures retain their separate explicit invalidation authority.

The review ledger includes every original proposal, its reason and exact values, reviewer decision or pending state, affected object identities, before/after byte hashes and post-fix automated findings. Role mapping includes transitively affected source elements. A successful structural check verifies the implemented invariants only; empty or reduced findings cannot establish semantic correctness or complete conformance. Accepted changes remain separate from `PdfAccessibility.Validate` and its explicit independent validator/human-review records. `HumanReviewRequired` remains true even if every proposal was accepted.

`WriteReview` writes bounded schema-one JSON with `conformanceVerified:false`, ordered outcomes and chained hashes. It includes the full proposed structure plan, reviewer notes and semantic text intentionally; it is an audit artifact, not sanitized telemetry. Callers own its privacy and retention choices. JSON output, staged PDFs, graph traversal, mapping chains, copies, snapshots and independent provider work remain subject to one operation context, resource limits and cancellation. Input/candidate PDFs are capped at 64 MiB, ledger output at 16 MiB and source documents at 10,000 pages, subject to stricter policy budgets.

## Role-map profile

An accepted `RoleMapping` adds or replaces one direct custom-to-standard PDF1 role mapping on an existing structure root. Standard roles cannot be remapped. Source inspection follows bounded named mapping chains, rejects cycles/malformed values and reports unresolved custom roles. Effective mapped Figure/Formula/Form roles retain alternative-text requirements, and mapped table roles retain remediation restrictions. Raw role names and element identities survive; no silent conversion to another raw role occurs.

Namespace-aware PDF2 role-map editing is not implemented by this profile and rejects explicitly. PDF/UA-2 element changes and complete standard-namespace author plans remain available through the existing contracts. Complete arbitrary role/namespace/class-map remediation, tree reparenting and inference quality remain pending scope.

## Source evidence and limitations

The original contract corpus covers pending/rejected/accepted decisions, exact source binding, immutable proposal arrays, failed later fixes and atomic output, direct/transitive role maps, mapped-description requirements, cyclic maps, explicit heading/list/table plans, cancellation and shared budgets. Compiled C# and Visual Basic consumers require an explicit caller decision; fixture decisions are labeled synthetic. No human or screen-reader review is claimed.

`eng/verify-semantic-review.py` independently validates JSON dispositions and byte-hash chains. Its optional pypdf/MuPDF mode checks structure parent links, MCID/parent-tree coverage, reading-order permutations, explicit role maps/author roles and unchanged 144 DPI fixture pixels. The pinned offline veraPDF validator exercises exact UA-1/UA-2 figure outputs after accepted description and order changes; automated success on those original fixtures is not general accessibility qualification.

See [exact source evidence](evidence/FP-101-source.json). A labeled real-document remediation corpus, qualified inference, manual screen-reader/semantic review, complete validators/profiles, actual minimum Framework 4.7.2, all required runtime/RID and final-package consumers, endurance and fuzzing remain mandatory. #93 remains user-skipped. No production gate or requirement status is relaxed.
