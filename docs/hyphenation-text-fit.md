# Explicit hyphenation and paper fit

`PdfHyphenationDictionary.Read` captures an offline whole-word exception dictionary with an exact SHA-256 pin, explicit language, version and provenance identifier. The SDK never discovers, downloads, normalizes or case-folds dictionary data. Provenance is caller-supplied metadata, not a license approval. No third-party dictionary ships in this source profile.

The bounded format is strict UTF-8 without a BOM, at most 2 MiB, with LF-terminated rows: `word`, a tab, and comma-separated increasing UTF-16 break offsets. Words are unique ordinal BMP sequences using pinned Unicode18 bidi L/R/AL/NSM or grapheme SpacingMark characters, excluding default ignorables and surrogates of at most128 units. Breaks must be interior extended-grapheme boundaries; splitting a combining sequence rejects. Duplicate words, malformed encodings, missing newlines, CRLF and incorrect source hashes reject. The original stream remains caller-owned. This format represents explicit custom exceptions, not a pattern dictionary or a claim of complete linguistic coverage.

`paragraph.WithHyphenation(dictionary)` returns an immutable copy; original runs and logical text are unchanged. Every run must explicitly match the dictionary language. The current managed profile requires an entirely bidi-level-zero paragraph; mixed-direction and right-to-left tailoring fail with `Hyphenation.DirectionUnsupported`. Unmatched words retain the existing overflow policy. Break candidates are reshaped with the visual hyphen before width acceptance, so the hyphen must fit too. A missing hyphen glyph fails through normal explicit font coverage. There is no automatic shrinking or silent clipping.

`PdfFlowLine.Text` retains the original logical slice; `HasDiscretionaryHyphen` identifies a visual addition. Its shaped text includes the hyphen, while its enclosing PDF `ActualText` contains the unchanged original slice. Raw glyph extraction may expose the hyphen; readers honoring `ActualText` can reconstruct the source. Complete copy/search interoperability and multilingual visual goldens remain mandatory. Dictionary capture and layout are separate bounded operations, with all lookup/shaping work charged to the layout context.

`PdfPageImposition.FitToPaper` fits each displayed source crop onto one sheet through the existing vector imposition engine. Positive caller-specified minimum and maximum scales bound uniform scaling; margins must leave a usable frame. A page that needs a scale below the floor rejects the entire result. The ceiling can prevent enlargement and leaves centered whitespace. Source crop semantics are retained: this does not discover ink outside the source crop or reflow text. Existing page/annotation/structure handling and explicit unsupported profiles still apply. Flow line-height/float exclusion, diagnosed clipping and explicit tile overlap continue to use their existing policies.

Browser CSS precedence remains explicitly controlled by `PdfHtmlPrintOptions.PreferCssPageSize`, with `Scale` and margins as documented in [HTML printing](html-printing.md). Browser fitting is not measured by this managed helper, and an unknown browser scale must never be reported as satisfying its minimum. The complete browser host, language dictionaries/rules, full overlap and multilingual corpus, production runtimes and exact final-package qualification remain open. See [source evidence](evidence/FP-111-source.json).
