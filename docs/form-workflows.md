# Field values, interchange and flattening

FP-037 has a managed source profile on net472, netstandard2.0, net8.0 and net10.0. It builds on [AcroForm field/widget editing](forms.md), uses the existing graph/stream/atomic-save boundaries and adds no runtime dependency. C#/VB `FillAndFlattenForm` consumers use public contracts and caller-provisioned fonts. Ordinary field processing never executes calculations, actions, imported scripts or XFA, and never opens a file-select path or a packet's external reference.

`PdfForms.ReadValues` extracts current data-bearing standard fields, retaining exact qualified names and raw button state/export names. It honors NoExport unless explicitly included; push/signature fields are excluded from value exchange. `PdfFormData` captures immutable null/name/text/text-array values with case-sensitive distinct names. A source text-stream value or richer field payload needs a separate decoding/data profile. Indexed button Opt labels remain inspectable; the value packet uses the exact V appearance-state identity, without guessing a label-to-state mapping.

`PdfFormData.Read`/`Write` require an explicit format. Every format has a sixteen MiB extent ceiling, additionally subject to operation input/output/expansion/object/depth/time limits. FDF accepts optional classic cross references, generation-zero indirect objects and direct/indirect hierarchical fields; supplied cross references are verified. The current V-only FDF profile emits T/V/Kids and rejects additional metadata/action/file/appearance import instructions. Full FDF option/instruction and file-selection interoperability remains mandatory work. XFDF emits standard field/value elements and preserves qualified hierarchy. Its values are strings; target field types restore exact button names on fill. Non-ASCII button byte names require an additional qualified XFDF encoding profile and reject. Null/empty-array distinctions are preserved in typed formats; XFDF carries the supported semantic string/selection view.

The original JSON schema is `{"version":1,"fields":[{"name":"Customer.Name","type":"text","value":"Ada"}]}`. Types are text/name/texts/null; duplicate properties, malformed Unicode/UTF-8, shape coercion, trailing tokens and unknown schema fields reject. The original XML namespace is `urn:fluent-pdf:form-data:1`, with a version-one form-data root and typed field/value children. Own-schema XML uses explicit UTF-8 base64 for text/name data outside XML's character repertoire. Standard XFDF rejects unrepresentable XML characters. XML readers prohibit DTDs/resolvers/entities and unknown instructions; there is no schema/network discovery. Parsing is separate from applying values and cannot mutate a document on failure.

`FillData` uses target kinds to restore button names. `Fill` accepts per-field `PdfFormUpdate` values/reset values and exact per-widget Forms or a `PdfFormTextStyle`. All widgets synchronize under the same operation context. Button V/AS preserves case-sensitive on/off states; choice V/I agrees with option order and I is authored only for multi-select lists. Single-line text rejects line breaks. Null entries follow PDF absence/inheritance rules. Valid same-name terminal representations update together with their named owner; a clear inherited from a differently named ancestor, or an owner shared with other logical fields, needs an explicit inheritance materialization profile. New absent fields cannot accidentally inherit source values. Only the attributes specified as inheritable propagate; choice Opt/I/TI and rich-text RV/DS stay with their owning field, while checkbox/radio Opt is inheritable.

Text generation uses explicitly supplied fonts/shaping and embeds private Unicode appearances. Password generation requires a caller-selected mask, and the appearance's ActualText contains the mask; a stored V remains unencrypted. Conservative bounds reject overflow. Current automatic generation covers left-aligned plain text and combo display text. Other alignment, list selection, comb, legacy representation styling, rich text and rollover/down value regeneration require explicit additional profiles or supplied supported private Forms. A source NeedAppearances request rejects by default; explicit retention diagnoses that a viewer may replace authored appearances. Updating one field does not silently disable regeneration for unrelated widgets.

`CopyField` copies one separate field/widget graph to an explicit new root partial name. Source and target names collide explicitly; every widget/navigation page needs a source-to-target mapping. Private resources are remapped, editing fonts receive collision-free target names and DA font operands are rebound. Unselected field-owner references, merged/legacy ownership splitting, tagged target creation and additional DA graphics/position/resource operators need further profiles. Imported calculations remain passive and append to target CO. Copied scripts/lock names require an explicit retention decision; source sessions/streams remain caller-owned. A signed value cannot be copied as a new signature.

`DecorateWidget` overlays a detached private Form on all existing N/R/D appearance states. It preserves exact widget identity, values, AS, actions and structure links. `Flatten` paints selected/all normal appearances in native page space, removes their widget/page and field-tree ownership, prunes empty containers and synchronizes CO/SigFlags. Remaining fields/widgets keep their identities. Annotation visibility, Form matrices/bounds and outer optional-content visibility are retained. Dynamic view flags, opacity/blend/page-group compositing and selected tagged-widget conversion require additional profiles. A surviving reference to a removed owner rejects the transaction. Opaque name references require explicit retention. Full rewrite prunes unreachable history/objects; flattening is not redaction.

Choose incremental mode explicitly when retaining original signature bytes. The returned document must also be saved incrementally; a later default full save still rejects signature rewriting. Existing nonselected signature dictionaries and signed byte prefixes are retained, but this does not verify cryptographic validity or permitted modifications. Certification/field-transform permissions require verification or explicit signature invalidation authorization, with a retained diagnostic. Removing a signed field requires the dedicated signing/removal profile. Full signing verification and independent signature qualification remain owned by FP-032.

Source tests and small independent FDF/XML/JSON/PDF/pixel checks are profile evidence. Full format/subtype/viewer/fidelity and structure corpora, the remaining source profiles, actual minimum runtimes, exact final package consumers and every production gate remain mandatory. NuGet packing and publication stay blocked.
