# Linearization and progressive access

`PdfProgressiveDocument` is an explicit caller-owned range session for passive syntax access. `ReadPage(index)` reads cross-reference indexes and the required page-tree dictionaries, applies the four inheritable page attributes, and leaves indirect content/resources as references. `ReadObject(id)` captures one object's encoded stream into detached immutable bytes; `DecodeStream(id)` resolves only its filter dependencies and returns detached decoded bytes. Cross-reference streams and object streams use the existing bounded managed parser. Encrypted progressive input rejects; no authentication or decryption engine is selected implicitly.

The caller supplies `IPdfRangeSource`. It checks authorization and returns an immutable nonsecret revision/length identity, then serves exact conditional ranges. Each operation checks authorization/identity even when every block is cached, checks again after reads, and rejects changed revisions, wrong bounds, truncated responses and extra bytes. The SDK owns returned response bodies and expires its borrowed leases at return; it never disposes the caller's source. Provider failures redact transport details. The source must enforce its own explicit TLS, origin, redirect, credential and conditional-request policy and cooperate with the mandatory context's cancellation/deadline. There is no default network transport or credential discovery.

Each session has its own byte-bounded LRU cache; there is no cross-document or tenant cache. Payload and bookkeeping allocations are charged before allocation, resident bytes are charged again to each new operation's budget, and misses consume cumulative input bytes. Indexes and parsed objects live only within their operation, preventing an unbounded persistent object cache. Failure clears cached blocks. A changed revision requires a new session. Concurrent use/disposal rejects; independent sessions may run independently. Source descriptors must identify immutable revisions: a provider that lies about byte identity cannot be repaired by the SDK.

Selective page access trusts declared counts for unvisited subtrees and does not validate an entire document, resolve all graphics dependencies, render a page or execute actions. It parses immediate child dictionaries on visited branches; large flat page trees can therefore require substantial index/dictionary access. Shared compressed object containers may require decoding the complete containing stream. The operation's resource limits still apply. Page dictionaries and returned object streams remain usable after session disposal. This syntax API does not create an editable document with partial validation.

`InspectLinearization` reports the first dictionary's exact file-length, page, primary-hint and first-section bounds. It does **not** validate every hint bit or establish web optimization. `PdfLinearization.Write`/`WriteFile` require an explicitly configured complete producer and a separately implemented complete independent validator. Both have pinned nonsecret identities, exact prerequisite checks before capture, explicit offline assets and one shared context. Native implementations require qualified bounded isolation. No complete producer, validator, native dependency or runtime download is bundled by this source change.

The write pipeline stages a candidate, reparses it, checks page inventory/geometry and requested first-page settings, binds the validator's complete zero-finding verdict to exact candidate/request SHA256, then copies to a borrowed stream or atomically replaces a file. The producer must retain all document semantics; geometry checks alone do not prove retention. Missing/incomplete/stale/failed verdicts expose no candidate. Caller stream I/O or cancellation during the final copy can still leave a partial caller stream; file replacement is atomic. Full rewrites require explicit signature invalidation authority. Ordinary SDK edits rewrite without the old linearization dictionary; obtaining a newly optimized file requires rebuilding and independently validating the exact edited bytes.

The C# and VB contract examples expose `ReadProgressivePage` and `WriteLinearized`. Original three-page fixtures have deterministic source generation in `eng/generate-progressive-fixtures.py`, using explicitly pinned task-local analysis tools. The producer's own hint check is retained as a development observation and is **not** independent hint validation. Contract verdict fixtures exercise binding/failure behavior and are not conformance engines. Actual loopback HTTP tests exercise authorization, conditional ranges, cache reuse and cancellation. Two unrelated PDF readers check controlled page geometry/rendering. No production latency threshold follows from these small fixtures.

The complete FP-073 scope remains mandatory: qualified producer/independent complete hint validation, broader range-aware encrypted/editing/rendering integration, real HTTP/authentication/security corpora, representative first-page latency/cache/endurance benchmarks, all actual runtime/RID/minimum Framework lanes and exact final package consumers remain open. These source contracts do not close the production requirement.
