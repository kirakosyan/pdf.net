# Password and certificate security source profile

FP-031 has an original managed security implementation and an optional offline CMS provider. This is source validation; production qualification and the remaining required profiles below are pending. Packing and NuGet publication remain blocked.

`PdfSecurity.EncryptWithPassword` takes a detached snapshot, borrowed output and disposable `PdfPassword` objects. New protection defaults to PDF 2.0 AES-256/revision 6. AES-128/revision 4 is an explicit compatibility choice; no RC4 or revision 5 authoring option exists. `DecryptWithPassword` distinguishes owner/user authentication, reports the file permissions and writes a full plaintext rewrite. Legacy RC4/revision 5 input requires `allowLegacyEncryption`. Wrong credentials fail before output is copied.

Passwords contain caller-prepared bytes: UTF-8 after standard password preparation for revision 6, or the specified legacy eight-bit encoding. The byte API never silently normalizes a string. Credentials are copied into private operation buffers, cleared after use and never included in reports. Dispose a password after concurrent operations have acquired their private copies. A complete Unicode 3.2 password-preparation convenience API remains required work; callers currently supply the prepared bytes themselves.

`EncryptWithCertificates` and `DecryptWithCertificate` require an explicit `IPdfCmsEnvelopeProvider` registration. Optional `Fluent.Pdf.Cryptography.ManagedCmsEnvelopeProvider` composes pinned System.Formats.Asn1 with platform RSA/AES; the core has no ASN.1 package dependency. Recipients snapshot public DER certificates only. A credential borrows an explicit RSA private-key handle. The SDK never searches certificate stores, exports private keys, discovers PINs, retrieves network trust or downloads binaries. Certificate validity, trust and hardware key-provider behavior are explicit caller responsibilities.

New public-key files use a document-wide `adbe.pkcs7.s5` filter with AES-256 or explicitly selected AES-128. Recipients are grouped by effective permissions, with one CMS envelope per group. Owner authority grants all permissions; PDF 2.0 accessibility restrictions are ignored. CMS output uses AES-256-CBC content encryption and RSA-OAEP-SHA256 by default. RSA PKCS#1 v1.5 output requires an explicit transport choice. Reading legacy S3/S4 RC4 files, RSA PKCS#1/SHA-1 transport and RC2/3DES CMS content requires explicit legacy permission. Weak algorithms are compatibility input, never an implicit fallback.

String, stream, embedded-file and explicit first `/Crypt` filters share the authenticated handler. Identity overrides, plaintext metadata policy, unencrypted cross-reference streams and signature `/Contents` have distinct handling. Object-stream containers decrypt before filter expansion; compressed child strings are not decrypted a second time. Direct and uncompressed indirect encryption dictionaries and stable incremental security history are supported. Changing handlers/permanent legacy IDs or indirect bootstrap security parameters fails with a typed diagnostic.

Both directions use one operation context through graph preparation, authentication, crypt filters, provider calls, parsing and full rewrite. Charge-before-allocation and cooperative checkpoints cover keys, recipient/DER inventories, digest input, ciphertext, decoded objects and staging. There are no SDK plaintext temporary files. Caller input/output streams and RSA handles stay owned by the caller. Plaintext output is an explicit caller destination; caller stream implementations control their own storage. Copying to a stream can leave partial output after an I/O error or cancellation. No path API is exposed by this profile.

Existing signatures block full rewrites by default. `allowSignatureInvalidation` explicitly permits a reported invalidating rewrite; it does not validate a signature or authorize an edit under certification permissions. `PdfSecurityResult.Permissions` records the authenticated handler flags; owner authority is separate. This low-level explicit decryption boundary does not enforce a Reader interaction policy or make permission flags a cryptographic access boundary after decryption. PDF CBC/RC4 protection does not provide document authenticity; use qualified signature verification for that claim.

C#/VB contract consumers demonstrate password protection/decryption and explicit CMS registration. All four library targets retain matching public contracts. Independent observations use original documents, public fictitious test credentials, published AES/RC4 vectors, independent password algorithms, independent PDF readers and CMS decryption. Retained failures and corrections are recorded in the evidence; they do not prove the full production corpus.

Required remaining profiles include independently keyed/multiple public-key crypt filters and embedded-only authentication, additional CMS recipient/BER/attribute/key-provider profiles, indirect security bootstrap and handler-change history, complete prepared-Unicode coverage, complete malformed-input/resource/cancellation/fuzz/concurrency/endurance campaigns, actual minimum OS/runtime/provider validation and exact final-package consumers. No required scope is removed.
