# Versioned business observations

FP-104 has a source implementation. Complete business-document reconstruction, real scanned/digital corpora, native OCR accuracy, minimum-runtime/RID and final-package qualification remain mandatory. Source export does not establish business correctness or production readiness.

`PdfBusinessData.Write` and `WriteFile` export exact schema version1 as UTF-8 JSON or XML. They capture the borrowed input at its current position, bind the result to its SHA-256 and stage all extraction/serialization before delivery. File output uses atomic replacement; ordinary output streams can still fail during the final copy. Caller streams remain open. The source limit is64MiB, with at most10000 pages; record and output byte ceilings are explicit and all nested extraction/render/OCR work shares one operation context.

The JSON contract is [business-data-v1.schema.json](../specs/business-data-v1.schema.json). XML uses `urn:fluent-pdf:business:1`, a closed [XSD vocabulary](../specs/business-data-v1.xsd), and scalar/array `type` attributes. XML field typing, uniqueness and record semantics must also pass the paired semantic rules in [the checker](../eng/verify-business-data.py); the XSD alone is not the complete semantic validator. A null field is distinct from an empty string or array. Both formats reject characters outside XML1.0's Unicode scalar repertoire so equivalent JSON/XML observations cannot silently disagree.

Compatibility is exact-version and fail-closed: this writer accepts only version1, and readers must validate the version/namespace before processing. Unknown schema versions, record kinds, fields, scalar types or duplicate properties must reject. Schema1 is frozen for existing field meanings and confidence units; incompatible changes require another version and an explicit migration. JSON and XML records have the same values and ordered arrays; JSON object property order is not semantic.

Every record has a stable local ID, a kind, provenance, nullable zero-based page index and source object identity, a nullable parent record ID and `businessVerified: false`. Object identities use `number:generation` and refer to the exact hashed input. Coordinates are displayed top-left physical points. Character and inferred table records name the owning page object; character operation indices are execution-order indices including nested Forms, not a claim to identify a unique encoded content stream. Table rule references additionally retain their source container/operator identity. Full nested occurrence reconstruction remains in the dedicated resource extraction API.

The exported observations are intentionally separate:

- Page records retain source-order decoded text, semantic replacements and inferred layout text. Their provenance is `mixed`: decoded strings may contain source mappings, inferred simple-font mappings or diagnosed unmapped values.
- Character records retain Unicode mapping provenance, encoded code/length, execution and character indices, visibility and estimated-geometry flags. Paragraph records retain geometric grouping and source indices, with no invented numeric confidence.
- Optional per-page tables retain merged cell spans, source character/rule references and uncalibrated heuristic scores. Numeric conversion occurs only with the caller's explicit culture and never verifies a business amount. Header/continuation aggregation rejects in this export profile.
- Passive form fields retain declared names, kinds, null/name/text/text-array values, all representation identities and widget associations. A declared field name is a source fact, not a verified semantic label. Complex/signature values reject rather than pretending to be ordinary business data. Widgets without a known page retain their identity but have no asserted displayed coordinates.
- Explicit structural inspection exports raw declared roles, language, ActualText, alternative text and ordered child associations, plus unresolved findings. It does not infer section meaning or assert accessibility conformance. Direct unsupported structural children reject.
- Optional OCR requires explicit renderer, recognition configuration, opaque integer isotropic DPI72–600, and explicit providers. It runs on the captured source pages and remains separate from existing digital text. Text/words retain engine/model identity, language and nullable engine scores in0–100. No score becomes a verified value or calibrated probability; no duplicates are silently removed. Pixel boxes map through the exact rendered region into displayed page coordinates.

No parser executes imported actions, field scripts, attachments or external resources through this API. PDF-internal source declarations can themselves be inaccurate. Consumers must review inferred labels and values before using them for business decisions; this schema has no API to promote an observation into verified data.

Seven original source artifacts exercise digital text, merged numeric tables, Unicode/control escaping, form values, declared structures, explicitly synthetic mixed OCR and compiled C#/VB consumers. Standard-library JSON/XML checks run in every hosted source lane. Local formal JSON Schema/XSD validation and independent PDF page/text checks are separately recorded in [source evidence](evidence/FP-104-source.json). The synthetic OCR provider tests context/geometry/provenance contracts only; it is not real OCR accuracy or a mixed business-corpus qualification. See [production gates](production-quality.md).
